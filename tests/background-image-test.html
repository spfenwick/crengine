position test suite

Combines a background-image scaling test suite covering background-size and screen-DPI scaling, an SVG/raster scaling comparison suite testing <img> against background-image side-by-side, a background-repeat tiling test suite, the background-position test cases, and the MathML radical symbol position regression tests (since the latter exercises background-position internally to anchor the synthesized radical symbol image).

background-image scaling test suite

Exercises the DPI-scaling fix in DrawBackgroundImage() (lvrend.cpp): the image's native pixel size is now passed through scaleForRenderDPI() before being used as the "no background-size" size or as the basis for auto/ cover/contain sizing — the same scaling getStyledImageSize() already applies to plain <img> elements. Before this fix, a background-image with no background-size was drawn at its raw file pixel size, which would mismatch a same-source <img> on any screen where gRenderDPI isn't 96. All cases below use the same 60×40 test image: a 6×4 grid of 10px checkerboard squares, with a red marker dot in the top-left cell and a green marker dot in the bottom-right cell (so cropping/orientation is easy to judge), inside a 2px black border. Any unintended stretch or squash shows up as non-square checkerboard cells.

1. Reference <img> vs. default background-size (no size specified)

left: plain <img>, no width/height set — sized however crengine scales images for the current gRenderDPI. right: a bordered box, deliberately larger than the image (120×80px) with background-repeat: no-repeat and no background-size declared.
expected: the checkerboard drawn in the right-hand box (top-left corner, unrepeated) is exactly the same pixel size as the reference <img> on the left — both should scale identically with gRenderDPI. A mismatch here means the background image is (still) using its raw file size instead of the DPI-scaled size.

2. Explicit background-size on both axes (independent, may distort)

background-size: 120px 40px; in a 120×40px box
expected: since both dimensions are given explicitly, the image stretches to exactly 120×40px regardless of its native size or gRenderDPI — width doubled, height unchanged, so the checkerboard cells become 20px wide × 10px tall (visibly non-square)

3. background-size with one axis auto (aspect ratio preserved)

background-size: 90px auto; in a 90×60px box
expected: width is scaled 1.5× (60px → 90px) and, since height is auto, it is derived from the (DPI-scaled) native aspect ratio, so it also scales 1.5× (40px → 60px) — the checkerboard cells stay square (15×15px), just larger, rather than being stretched only horizontally. This confirms the aspect-ratio math uses the DPI-scaled width and height consistently, so the ratio comes out right regardless of gRenderDPI.

4. background-size: cover

background-size: cover; in a 150×40px box (much wider than the image's 3:2 aspect ratio)
expected: the image is scaled up (uniformly, no distortion — cells stay square) until it fully covers the box, then cropped; since background-position defaults to top left, the crop comes off the right/bottom, so the red top-left marker should remain visible while the green bottom-right marker is cropped away

5. background-size: contain

background-size: contain; in a 150×120px box (5:4, clearly wider-relative-to-its-height than the image's 3:2 native ratio, so a sizable leftover strip is unmissable); box background-color overridden to a non-white pink so that strip is obvious against the page
expected: the image is scaled up uniformly (no distortion — cells stay square) by the smaller of the two axis scale factors (width: 150/60 = 2.5×, height: 120/40 = 3×, so 2.5× is used), landing at 150×100px — full width, with no cropping, so both the red and green corner markers remain visible; since background-position defaults to top left, the image sits flush in the top-left corner of the box, leaving a 20px-tall pink strip of bare background-color along the bottom

SVG and raster image scaling comparison

Compares a plain <img> against the same source used as a background-image, side by side, using two small images: a 16×16 vector SVG icon (a filled circle with a border — curved edges show up scaling/anti-aliasing differences much more clearly than a straight diagonal line does) and an 8×8 low-resolution raster PNG checkerboard (alternating black/white pixels, with a red marker pixel top-left and a green marker pixel bottom-right). Each image is tested once at its default (no explicit size, DPI-scaled) rendering and once at an explicit larger size, so both whether <img> and background-image agree on scaled dimensions, and how the scaling itself is done, can be judged. The SVG cases mainly test that both paths apply the same DPI scaling and stay equally crisp (vector data has no native pixels to lose, and a circle's curve will look faceted/polygonal rather than round if it's being rasterized incorrectly). The raster cases are the more revealing ones: at 8×8 native size scaled well past it, any pixelation (hard, stair-stepped square edges — nearest-neighbor scaling) versus smoothing (soft, blended edges — interpolated scaling) becomes obvious, and whether <img> and background-image apply the same treatment becomes easy to see. A final case checks that the SVG icon decodes identically regardless of data URI encoding (percent-encoded vs base64) and regardless of which of the two elements references it.

1. Small SVG icon — default size (<img> vs background-image)

left: plain <img>, no width/height set. right: the same SVG as background-image, no background-size declared, in a 40×40px box.
expected: since both paths run the native 16×16 SVG size through the same DPI scaling, the two renderings should be pixel-identical in size, and the diagonal edge should look equally sharp in both — there's no raster data to pixelate, so this should hold regardless of gRenderDPI.

background-image, no background-size,
in a 40×40px box

2. Small SVG icon — explicit dimensions (<img> vs background-image)

left: <img> with width="64" height="64" (4× the SVG's native 16×16). right: the same SVG as background-image with background-size: 64px 64px, in a 64×64px box.
expected: with an explicit size on both, DPI scaling doesn't come into play — the two should render at exactly the same 64×64px size and, since the source is vector, the diagonal edge should still be smooth/anti-aliased rather than pixelated at this larger size, with no visible difference between the two.
<img>, 64×64

3. Low-resolution raster image — default size (<img> vs background-image)

left: plain <img>, no width/height set, using an 8×8px raster PNG checkerboard. right: the same PNG as background-image, no background-size declared, in a 40×40px box.
this raster image is only 8×8 native pixels, so unlike the SVG cases above, any scaling applied by scaleForRenderDPI() (even the default 1:1 at 96 DPI) has real per-pixel raster data to work with. Look closely at the edges between checkerboard squares: hard, stair-stepped edges mean nearest-neighbor scaling; soft, blended edges mean the squares are being smoothed/interpolated. Compare the <img> and background-image renderings to check whether they apply the same treatment.

in a 40×40px box

4. Low-resolution raster image — explicit upscaled dimensions (<img> vs background-image)

left: <img> with width="96" height="96" (12× the PNG's native 8×8). right: the same PNG as background-image with background-size: 96px 96px, in a 96×96px box.
at 12× magnification, pixelation (if the scaler is nearest-neighbor) or blurring (if it's smoothed/interpolated) will be unmistakable — each native pixel should appear as either a crisp 12×12px block or a softened blob depending on which algorithm is used. Compare the two renderings for both the presence of pixelation and whether <img> and background-image apply it consistently.
<img>, 96×96
background-image, background-size: 96px 96px

5. SVG data URI encoding — percent-encoded vs base64 (<img> vs background-image)

the exact same 16×16 SVG icon markup (from cases 1 and 2 above), encoded two different ways as a data URI — percent-encoded (data:image/svg+xml,%3Csvg...) and base64-encoded (data:image/svg+xml;base64,...) — each rendered both as an <img> and as a background-image, all four at the SVG's native 16×16 size.
expected: all four tiles are pixel-identical — the encoding is just a transport format for the same underlying SVG bytes, so decoding either form (and rendering it via either the <img> or background-image path) must produce the same result. Any visible difference (missing image, wrong colors, wrong size) indicates a bug in the base64 or percent-decoding, or a discrepancy between the two rendering paths.

background-repeat test suite

Exercises the tiling logic in DrawBackgroundImage() (lvrend.cpp), which supports the four keywords crengine parses for background-repeat: repeat (the initial value), repeat-x, repeat-y, and no-repeat (the CSS round/space keywords aren't implemented). All cases use the same 20×20 tile: a diagonal split into a blue triangle (top-left) and an orange triangle (bottom-right), with a border around the tile. Where tiles correctly abut with no gap or overlap, the diagonal edges line up into a continuous zigzag; any seam, gap, or doubled border between adjacent tiles indicates a tiling regression.

1. background-repeat: repeat

background-repeat: repeat; in a 205×103px box (deliberately not a multiple of the 20px tile, to show edge clipping)
expected: the tile fills the box in both directions from the top-left corner, with the diagonal zigzag continuing unbroken across tile boundaries; the rightmost column and bottom row of tiles are partially clipped by the box edges (10×20px / 20×3px / 10×3px remainders) rather than leaving a gap or squeezing in an extra part-tile

2. Default (property not set)

no background-repeat declared, same 205×103px box
expected: identical to case 1 — repeat is the initial value

3. background-repeat: repeat-x

background-repeat: repeat-x; in a 205×60px box
expected: a single row of tiles across the full width along the top edge (default background-position: 0% 0%), clipped on the right; no tiling downward — the rest of the box below the row shows only the plain background-color

4. background-repeat: repeat-y

background-repeat: repeat-y; in a 60px×103px box
expected: a single column of tiles down the full height along the left edge, clipped on the bottom; no tiling rightward — the rest of the box to the right of the column shows only the plain background-color

5. background-repeat: no-repeat

background-repeat: no-repeat; in a 60×60px box
expected: a single tile in the top-left corner only; the rest of the box shows only the plain background-color

6. background-repeat: repeat with an offset background-position

background-repeat: repeat; background-position: 10px 10px; in the same 205×103px box as case 1
expected: tiling is phase-shifted so that a full tile's top-left corner sits exactly at (10px, 10px) — unlike case 1, this means partial tiles now also appear along the top and left edges (10×10px in the corner, 10px-tall strips along the top, 10px-wide strips along the left), not just the right/bottom; this checks that tiling phase is computed from the resolved background-position, not just always anchored at 0,0

7. Case-insensitivity

background-repeat: Repeat-X; in a 205×60px box
expected: same as repeat-x (case 3): keywords are ASCII case-insensitive

background-position test suite

Every box below is 200×110px with a light fill and a 1px border, and carries the same 24×24px target-marker image (a small red crosshair), background-repeat: no-repeat, background-size: 24px 24px. Only background-position changes between cases — the box's border marks the 0%/100% edges on each axis, so the marker's position within the box shows what the declaration resolved to. Some declarations resolve to a position partly or fully outside the box; since backgrounds are clipped to the border box by default, only the portion of the marker that falls inside the box is actually painted, so those cases will show a partial marker (or none at all) rather than the full crosshair extending past the border. This suite only covers the 1-value and 2-value forms of background-position (no attached-offset "edge" form, e.g. right 10px bottom 20px).

1. Default (property not set)

no background-position declared
expected: initial value 0% 0% (top left)

2. One value — keywords

background-position: left;
expected: left edge, vertically centered
background-position: right;
expected: right edge, vertically centered
background-position: top;
expected: top edge, horizontally centered
background-position: bottom;
expected: bottom edge, horizontally centered
background-position: center;
expected: centered on both axes

3. One value — percentages and lengths

background-position: 0%;
expected: same as left
background-position: 25%;
expected: 25% across, vertically centered
background-position: 50%;
expected: same as center
background-position: 75%;
expected: 75% across, vertically centered
background-position: 100%;
expected: same as right
background-position: -10%;
negative percentage (valid: percentages aren't clamped) — expected: the computed position sits slightly left of the box's left edge, but backgrounds are clipped to the border box, so only a thin sliver of the marker is visible at the left edge (the rest is clipped off), vertically centered
background-position: 120%;
percentage over 100% (valid) — expected: the computed position sits slightly right of the box's right edge, but backgrounds are clipped to the border box, so only a thin sliver of the marker is visible at the right edge (the rest is clipped off), vertically centered
background-position: 20px;
expected: 20px from left, vertically centered
background-position: -20px;
expected: the computed position sits 20px to the left of the box, but backgrounds are clipped to the border box, so only a 4px-wide sliver of the marker (its right edge) is visible at the left border — the rest is clipped off, vertically centered
background-position: 2em;
expected: 2em from left (font-relative unit), vertically centered

4. Two values — keyword pairs

expected: top-left corner
background-position: right top;

expected: bottom-left corner
background-position: right bottom;
expected: bottom-right corner
background-position: center center;
expected: centered on both axes
background-position: center top;
expected: top edge, horizontally centered
background-position: left center;
expected: left edge, vertically centered
background-position: top right;
reversed keyword order (still no attached offsets) — expected: same as right top (top-right corner)
background-position: bottom left;
reversed keyword order — expected: same as left bottom (bottom-left corner)

5. Two values — percentages and lengths

background-position: 25% 75%;
expected: 25% across, 75% down
background-position: 75% 25%;
expected: 75% across, 25% down
background-position: 0% 100%;
expected: same as left bottom
background-position: 100% 0%;
expected: same as right top
background-position: 20px 30px;
expected: 20px from left, 30px from top
background-position: -10px -10px;
expected: the computed position sits 10px above and 10px left of the box, but backgrounds are clipped to the border box, so only a 14×14px corner of the marker is visible at the top-left — the rest is clipped off
background-position: 20px 50%;
mixed length/percent — expected: 20px from left, vertically centered

6. Two values — keyword combined with percentage/length

These are the strict-order, no-attached-offset combinations: a horizontal-slot token (left/center/right/ <percentage or length>) followed by a vertical-slot token (top/center/bottom/<percentage or length>). Note the quirky cases at the end: a lone edge keyword followed by a bare number does not mean "offset from that edge" here — that meaning only applies to the attached-offset form (out of scope for this suite), so the number is taken as a position on the other axis instead.

background-position: left 25%;
expected: left edge, 25% down
background-position: 75% top;
expected: 75% across, top edge
background-position: center 30px;
expected: horizontally centered, 30px from top
background-position: right 10px;
quirk: only one keyword and it's in the horizontal slot, so 10px is the vertical value — expected: right edge, 10px from top (not "10px in from the right edge")
background-position: 10px bottom;
expected: 10px from left, bottom edge

7. Case-insensitivity

CSS keywords are ASCII case-insensitive, so mixed/upper-case spellings of the same keywords must resolve identically to their lower-case forms.

background-position: LEFT;
expected: same as left (left edge, vertically centered)
background-position: Center;
expected: same as center (centered on both axes)
background-position: Right Bottom;
expected: same as right bottom (bottom-right corner)
background-position: TOP RIGHT;
expected: same as top right / right top (top-right corner)

8. Invalid values (property should be ignored)

Per the CSS Backgrounds spec grammar for <bg-position>, none of these have a legal 1- or 2-value interpretation, so the whole declaration should be dropped and the property should fall back to its initial value (0% 0%, top left) — same as section 1.

background-position: top bottom;
invalid: both tokens can only fill the vertical slot, leaving the required horizontal component unfilled — expected: falls back to top left
background-position: left right;
invalid: both tokens can only fill the horizontal slot — expected: falls back to top left
background-position: top 10px;
invalid: 10px can only attach as an offset to a preceding left/right/ top/bottom keyword within its own axis, so "top 10px" is entirely a vertical-side component, leaving the required horizontal component unfilled — expected: falls back to top left
background-position: 10px left;
invalid: a bare <length-percentage> must be the first component when paired with a keyword, and can never stand alone unattached to a keyword — expected: falls back to top left
background-position: middle;
invalid: middle is not a background-position keyword (that's center) — expected: falls back to top left
background-position: banana;
invalid: unrecognized token — expected: falls back to top left

9. Three- and four-value edge-offset form

CSS also defines a 3-/4-value "edge-offset" form of <bg-position> (eg. right 10px bottom 20px), which lets a length/percentage be measured as an inset from the right/bottom edge instead of always from the near (left/top) edge. This is now supported. A percentage offset is always reducible to a plain percentage (right 20% == calc(100% - 20%) == 80%); a length offset (px, em, etc.) can't be reduced that way, so it's resolved at render time as (container size − image size) − offset. Trimmed to a small sample (rather than the full matrix) so this file can also be run unmodified against a branch that predates 3-/4-value support: on such a branch, the whole declaration in every case below is unrecognized and must be rejected, falling back to top left, exactly like section 10.

background-position: right 10px bottom 20px;
4-value form — expected (with support): 10px in from the right edge, 20px up from the bottom edge. expected (without support): falls back to top left
background-position: right 20% bottom 10%;
4-value form with percentage offsets, which reduce directly to a plain percentage — expected (with support): identical to background-position: 80% 90%;. expected (without support): falls back to top left
background-position: right 10px top;
3-value form: only the horizontal component has an offset attached, the vertical component (top) has an implied zero offset — expected (with support): 10px in from the right edge, at the top edge (contrast with the quirky 2-value right 10px in section 6, which instead means "right edge, 10px from the top"). expected (without support): falls back to top left

10. Still-invalid edge-offset combinations (rejected)

Not every combination of keywords and offsets is valid under the extended grammar — these should still fall back to the initial value (0% 0%, top left), same as section 8, rather than being misinterpreted. Also trimmed to a small sample; on a branch without 3-/4-value support these fall back to top left too (trivially, since none of it is recognized), same as section 9 without support.

background-position: right 10px left;
invalid: both components are forced horizontal (right/left), leaving the vertical component unfilled — expected: falls back to top left
background-position: right 10px bottom 20px 30px;
invalid: a 5th token can't be part of any valid background-position — expected: falls back to top left (not "10px from the right, 20px from the bottom, ignoring the trailing 30px")

MathML radical symbol position test

Exercises the code path in mathml.cpp's setMathMLElementNodeStyle() that draws the radical (√) symbol as a synthesized SVG background-image on the msqrt/mroot root-symbol cell, anchored with background-position: 100% 100% (bottom-right of the cell). This was previously set via the fixed keyword-pair enum css_background_right_bottom; now that background-position is stored as two arbitrary css_length_t values instead of a closed set of keyword pairs, it is set directly as two 100% css_length_t percentages. The dashed blue border around each formula outlines the <math> element's box, making it easier to see whether the symbol is flush with the bottom of its cell as expected.

1. Plain msqrt — short radicand

expected: the hook of the radical sign sits right at the baseline of "x", with the diagonal stroke rising to meet the horizontal bar above the radicand — no gap or misalignment at the bottom
x

2. msqrt with a tall radicand (fraction)

the fraction makes the root symbol's cell noticeably taller than the symbol's own natural size — this is the key regression case for background-position: since the symbol image is anchored bottom-right, its hook must still meet the bottom of the cell (and the radicand's baseline) even though the cell has grown taller; anchored top-left instead, the symbol would float near the top of the cell with a visible gap underneath
ab

3. mroot — cube root with an index

expected: small "3" index sits above-left of the root symbol; the symbol's hook still meets the radicand's baseline at the bottom
x3

4. mroot with a tall radicand

combines the index-cell layout from case 3 with the tall-radicand case from case 2 — the symbol must still hug the bottom-right of its (now taller) cell
ab3

5. Nested msqrt

a root inside a root — both radical symbols must independently anchor to the bottom of their own cell
x

6. Font-size scaling

font-size: 2.5em on the <math> element — the radical symbol is regenerated at the larger size (getRadicalSymbolSVGImageString is called with the resolved font size), so it must still be aligned to the bottom-right of its (now larger) cell, not just scaled up from a stale position
x

7. displaystyle attribute

displaystyle="true" — this makes the cell use the display-style vertical gap metric instead of the compact one, changing the cell's height; the symbol must still anchor correctly regardless of which gap metric was used
ab

Expected behaviour

In every case above, the diagonal check-mark stroke of the radical symbol should visually connect: its lower hook touches the baseline/bottom of the radicand content, and its upper tip touches the left end of the horizontal bar drawn over the radicand (the cell's top/left border). If the symbol image were left- or top-aligned within its cell instead of anchored bottom-right, you would see it detached from the bar and radicand, floating with a visible gap underneath — most obviously in cases 2, 4, and 7, where the cell is noticeably taller than the symbol itself.
